# i9 known state

Facts and decisions that earlier audits recorded, which change how audit signals are judged. An entry can be stale, wrong, or incomplete, and the machine changes between runs: confirm each one against this run's evidence before relying on it, and correct it when the evidence disagrees. Date each decision and open finding, give its reason and rollback, and delete an entry once its subject is gone.

## Host

- The primary link is Wi-Fi `wlo1`. `enp3s0` is a direct Ethernet link (10.42.0.2/24, `/etc/netplan/70-direct-link.yaml`), usually without carrier. networkd's `off` state means administratively down or being deleted; a Wi-Fi drop is `no-carrier` or `dormant`.
- `/etc/netplan/60-wifi.yaml` and its `.backup-*` copy hold the Wi-Fi password.
- `/tmp` is tmpfs, so its files use RAM, up to half of it. `systemd-tmpfiles-clean` deletes entries older than 10 days and a reboot empties it. Agent work accumulates there, in bursts: on 2026-10-09 at 20:10, 4.6 days after boot, 10.6 GiB had built up; by 23:10 it was 15 GiB (31% of `/tmp`), because a review subagent of a session started before the worktree rule below copied `nm/site` five times, `node_modules` included and not hardlinked, into `/tmp/review-final` (4.2 GiB in 15 minutes). Vitest's leaked temp directories (see Open findings) held 4.9 GiB and agents' named scratch directories most of the rest. The mean rate, 3.2 GiB a day, projects to about 32 GiB (70% of `/tmp`, 35% of RAM) once the 10-day cleanup starts, leaving about 48 GiB (52%) of RAM available. That leaves memory far from pressure, so the 10-day retention stays: a shorter one would free RAM nothing needs and delete files still in use, such as scripts that running dev tools loaded from `/tmp`. Agent job worktrees belong in `~/code/.worktrees` (global `CLAUDE.md` and `AGENTS.md`, 2026-10-09): bun cannot hardlink across filesystems, so a umath worktree in `/tmp` holds a 1.1 GiB copy of `node_modules` in RAM, while on disk it hardlinks every file from bun's cache.
- `w` owns the machine. `heila` is a separate user with a loop-mounted home at `/home/heila`, their own herdr server and agents, and podman containers. Processes listed under `usbmux` belong to the Supabase containers, whose UID matches that host user.
- Podman's `conmon` logs container stderr at error priority, so ordinary container stderr appears as journal errors under the container's name. `catatonit -P` is podman's rootless pause process, one per user who has run podman.
- NVMe `unsafe_shutdowns` was 39 on 2026-10-07.

## Exposure baseline

- ufw denies incoming by default. Its rules, identical for IPv4 and IPv6 except the 10.42.0.0/24 rule: allow anything on `tailscale0`, allow 22/tcp and 2222/tcp on `tailscale0`, allow 22/tcp from 10.42.0.0/24, deny 5678/udp on `wlo1`.
- Docker publishes Supabase on `0.0.0.0:54321-54324`, which bypasses ufw. The `DOCKER-USER` chains from `/etc/ufw/after.rules` and `/etc/ufw/after6.rules` drop forwarded traffic to Docker networks unless it comes from `tailscale0` or a Docker bridge: two DROP rules per address family. ingress-guard's forward chain also drops that Wi-Fi traffic, so either layer alone keeps published ports off the Wi-Fi network.
- `ingress-guard.service` loads `/etc/nftables.d/ingress-guard.nft`, the `inet ingress_guard` table, which filters at prerouting and forward, before ufw. From `tailscale0` it accepts m4 (100.102.28.20 and fd7a:115c:a1e0::c638:1c14), established and related traffic, ICMP, TCP 2222, 3000-3999, 5173 and 8000-8999, and UDP 60000-61000, and drops the rest; it also drops DNAT-ed traffic arriving on `wlo1` or `enp3s0`. Other tailnet devices therefore reach only those ports and Tailscale SSH on 22, which tailscaled answers before the kernel firewall sees it; a host listener outside them, even on `*`, is reachable only from m4. Tailscale itself filters nothing here: i9's packet filter accepts every port from every peer, including the six devices of the two users i9 is shared with, which plain `tailscale status` hides (they appear with `ShareeNode` in `tailscale status --json`; `sudo tailscale debug netmap` shows the filter and the SSH policy).
- sshd is socket-activated on 22 and 2222, with password and keyboard-interactive authentication and root login off; `AllowUsers` names `w`, `heila` and `i9-tunnel` (see Accepted decisions). Tailscale SSH is on (`RunSSH`): its policy accepts heila's device as `heila`, and asks m4 and the iPhone for a browser check every 12 hours, which the netmap shows as an accept rule for m4 with `ruleExpires`.
- Expected non-loopback listeners: ports 22 and 2222 (systemd socket activation for sshd), docker-proxy on 54321-54324, tailscaled on 41641/udp and its tailnet addresses, cloudflared's outbound QUIC sockets, and the DHCP client on `wlo1`.
- caddy serves 127.0.0.1:80 behind the cloudflared tunnel; cloudflared's metrics are on 127.0.0.1:20241.

## Expected processes and services

- The Mac's `i9-tunnel` LaunchAgent forwards ports 3000-3099 and 54321-54324 to i9's 127.0.0.1 through sshd on port 2222 as `i9-tunnel`, so an `sshd-session` client on those ports is the Mac using that server (a `tailscaled` client is an interactive `ssh -L` from the Mac). Its `agent-sounds-tunnel` LaunchAgent holds a reverse forward the same way, so `sshd-session` listens on 127.0.0.1:47123, where `~/.claude/play-notification.sh` sends agent sounds for the Mac to play.
- Agent sessions run in herdr panes, and each Claude Code or Codex session runs its own language servers, 0.1-1.4 GiB each. `herdr server`, `claude daemon run`, `claude bg-pty-host`, and `codex app-server` run detached by design. Agent jobs sometimes load every CPU on purpose: on 2026-10-09 a Codex job reproducing a flaky umath test ran 32 `while :; do :; done` loops under `timeout 1700s`, raising CPU `some avg300` to 48% with no memory or io pressure. Before treating CPU pressure as a fault, look for such a bounded load generator and its owning session.
- The user unit `moshi-hook.service` runs `~/.local/bin/moshi-hook serve` and listens on 127.0.0.1:24543.
- Dev servers started by agent sessions outlive them: `bun run dev` in an umath checkout runs `scripts/serve-cc.ts`, and `next dev` runs in `nm/site`. Judge each by the evidence rules, never by detachment alone. Agents bind them to 127.0.0.1 on 3000-3099 and give the user the Mac's `localhost` URL (global `CLAUDE.md` and `AGENTS.md`, 2026-10-10); a listener on the tailnet address or `*` in 3000-3999 is reachable by the shared devices.
- Every umath checkout (`umath_1` to `umath_4`) sets Supabase `project_id = "umath"`, so they share one stack (`supabase_*_umath`) and its volumes. Docker also runs `umath-browser` (Playwright run-server on the host network, 127.0.0.1:39093).
- After a `containerd.io` upgrade, needrestart lists `containerd.service` under `NEEDRESTART-SVC` until each container started before it is restarted: each container's `containerd-shim-runc-v2` keeps running the replaced binary, and restarting containerd does not replace it (2026-10-09).
- `webapps-backup.timer` backs the web apps up daily with restic into `/var/backups/webapps` (keeping 7 daily, 4 weekly, and 6 monthly snapshots) and pings healthchecks. `webapps-health.timer` checks them every 2 minutes. The user timer `neuramance-deploy.timer` polls every 10 seconds and is tracked in the dotfiles; an idle poll asks the GitHub API for `main`'s sha and logs nothing, so its journal holds only deploys and failures.
- `reboot-check.timer` runs `/usr/local/sbin/reboot-check` hourly and pings healthchecks with its output; a run fails while `/run/reboot-required` exists or `nvidia-smi -L` lists no GPU. Ubuntu's kernel hooks write that flag, naming `linux-image-<version>` and `linux-base`, whenever a package for an installed kernel changes, including a packaging-only `linux-modules-nvidia` rebuild for the running kernel (2026-10-08). NVIDIA is the only separately packaged module loaded. A flag naming only `linux-image-$(uname -r)` and `linux-base` is stale when `NEEDRESTART-KSTA` is 1 and `/sys/module/nvidia/srcversion` equals `modinfo -F srcversion nvidia`; clear it with `sudo rm /run/reboot-required /run/reboot-required.pkgs && sudo systemctl start reboot-check.service`. The check honours every flag entry on purpose, because a real NVIDIA driver update (595.58 to 595.71 on 2026-05-20) writes the same flag.

## Accepted decisions

- 2026-10-07: chrony's networkd-dispatcher `off.d` hook is diverted to `/usr/lib/networkd-dispatcher/off.d-chrony-onoffline.disabled`. On this host it fired only when Docker deleted an interface, where it does nothing, and each such event logged a `networkctl` error and a dispatcher `Failed to get interface` error. The routable hook remains. Verified: three Docker network create-and-remove cycles logged 12 `networkctl` errors before and 0 after, and the next 25 interface events logged no `Failed to get interface` line (210 earlier that boot). Still expected, and unaffected by the divert: `WARNING:Unknown index N seen, reloading interface list` for each new Docker interface, and an occasional `ERROR:Unknown interface index N seen even after reload` (at info priority) when an interface disappears before the dispatcher reloads, an upstream race. Undo: `sudo dpkg-divert --local --rename --remove /usr/lib/networkd-dispatcher/off.d/chrony-onoffline`.
- 2026-10-09: `/etc/systemd/network/10-netplan-enp3s0.network.d/optional.conf` sets `RequiredForOnline=no` for `enp3s0`. netplan 1.2 turns `optional: true` only into its drop-in for the boot-time `systemd-networkd-wait-online.service` (`-i wlo1`), but `apt-daily` and `apt-daily-upgrade` run `apt-helper wait-online`, which calls `systemd-networkd-wait-online` without `-i`, so each run waited the full 30 seconds for `enp3s0`, which has no carrier, and logged an error: 18 runs that boot. The drop-in was written on 2026-10-05, but networkd loaded it only at `sudo networkctl reload` on 2026-10-09, which reconfigured `enp3s0` alone. Verified: `systemd-networkd-wait-online --timeout=5` exited 1 after 5.2 seconds before; after, it and `apt-helper wait-online` exit 0 at once. The directory name follows netplan's generated `10-netplan-enp3s0.network`. Undo: `sudo rm -r /etc/systemd/network/10-netplan-enp3s0.network.d && sudo networkctl reload`.
- 2026-10-10: m4's `i9-tunnel` and `agent-sounds-tunnel` LaunchAgents log in to sshd on port 2222 as `i9-tunnel` (uid 101), a system account with no shell or home, instead of through Tailscale SSH. Tailscale SSH's 12-hour check left a reconnecting tunnel waiting 30 minutes and then failing (`failed to fetch next SSH action: fetch failed from https://unused/machine/ssh/wait/...`): that boot, 72 of 1,448 m4 connections to `w@i9` failed so, mostly in pairs, and none got through from 06:15 to 16:00 UTC on 2026-10-08 or from 04:00 to 15:30 UTC on 2026-10-09. `/etc/ssh/sshd_config.d/99-i9-tunnel.conf` limits the account to forwards to 127.0.0.1:3000-3099 and 54321-54324 and a listener on 127.0.0.1:47123, refuses its commands (`ForceCommand /usr/sbin/nologin`) and Unix-socket forwards (`w` is in the docker group, so a forward to `docker.sock` would be root), and drops an unresponsive connection within about a minute, freeing 47123. `/etc/ssh/i9-tunnel.authorized_keys` holds m4's `~/.ssh/i9-tunnel` key behind `restrict,port-forwarding` and `from=` m4's tailnet addresses, and `90-access.conf` adds the account to `AllowUsers`. Verified: `sshd -T` for `w` and `heila` on 22 and 2222 differs only by `allowusers i9-tunnel`; from m4, the key forwarded to 127.0.0.1:3001, and sshd denied a forward to 127.0.0.1:2019, a forward to `/var/run/docker.sock`, a command (nologin, exit 1), and listeners on 127.0.0.1:47124 and 0.0.0.0:47123; the same `from=` line refused a key offered from i9's own address; after the LaunchAgents reloaded, each connected on its first attempt, `sshd-session` held 127.0.0.1:47123, and a sound sent there got `ok`; with the Mac's reverse-tunnel client frozen by SIGSTOP, sshd logged `Timeout, client not responding` and freed 47123 after 61 seconds, and the resumed tunnel rebound it within 5 seconds. At 04:03 UTC, after the accept rule that m4's last check had granted expired at 04:01:44, `launchctl kickstart -k` of both LaunchAgents reconnected each within a second, where Tailscale SSH would have held them in check. The LaunchAgents pass `IdentityAgent=none`, so they never depend on, or add the tunnel key to, the Mac's SSH agent (`ssh -G i9` on m4 shows `addkeystoagent true`). The README's `i9-tunnel` section recreates every root-owned piece. Interactive logins keep Tailscale SSH and its check. `local-state backup i9` still logs in through it at 13:00 CDT, after the lapse windows seen so far, and fails if nobody has passed the check that day. Undo: on m4, revert dotfiles commit `44faa3e` and reload both LaunchAgents with `launchctl bootout` and `launchctl bootstrap`; then on i9, `sudo rm /etc/ssh/sshd_config.d/99-i9-tunnel.conf /etc/ssh/i9-tunnel.authorized_keys && sudo sed -i 's/^AllowUsers w heila i9-tunnel$/AllowUsers w heila/' /etc/ssh/sshd_config.d/90-access.conf && sudo sshd -t && sudo systemctl reload ssh && sudo userdel i9-tunnel`.

## Open findings

- 2026-10-09: umath pinned `vitest` 5.0.1, which never removes its run-wide temp directory (vitest-dev/vitest#11224, fixed in 5.0.3), so every run, clean or not, leaves `/tmp/<21-character id>/ssr/` holding the modules it transformed, about 3.9 MB. That day 1,250 such directories from the six umath checkouts held 4.8 GiB, 45% of `/tmp`. Verified: three clean runs of a one-test project left three directories with 5.0.1 and none with 5.0.3. umath PR #230, merged into `development` as `ad8aa870`, pins 5.0.3 and carries umath's Vitest patch to it (a plain version bump would drop the patch). A checkout stops leaking once it runs `bun install` on a commit that includes the merge: `umath_3` to `umath_6` did on 2026-10-09; `umath_1` and `umath_2`, on feature branches, still run 5.0.1. Delete this entry once they have the merge. The leaked directories hold only regenerable output and age out with the 10-day cleanup.
