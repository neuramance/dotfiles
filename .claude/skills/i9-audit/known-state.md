## Host

- The primary link is Wi-Fi `wlo1`. `enp3s0` is a direct Ethernet link (10.42.0.2/24, `/etc/netplan/70-direct-link.yaml`), usually without carrier. networkd's `off` state means administratively down or being deleted; a Wi-Fi drop is `no-carrier` or `dormant`.
- `/etc/netplan/60-wifi.yaml` and its `.backup-*` copy hold the Wi-Fi passwords; `/etc/wpa_supplicant/eap.conf` holds the 802.1X network's identity and NT password hash (see Accepted decisions, 2026-11-04).
- `/tmp` is tmpfs, so its files use RAM, up to half of it. `systemd-tmpfiles-clean` deletes entries older than 10 days and a reboot empties it. Agent work accumulates there, in bursts: on 2026-10-09 at 20:10, 4.6 days after boot, 10.6 GiB had built up; by 23:10 it was 15 GiB (31% of `/tmp`), because a review subagent of a session started before the worktree rule below copied `nm/site` five times, `node_modules` included and not hardlinked, into `/tmp/review-final` (4.2 GiB in 15 minutes). Vitest 5.0.1's leaked temp directories (fixed in 5.0.3; see Accepted decisions, 2026-10-21) held 4.9 GiB and agents' named scratch directories most of the rest. The mean rate, 3.2 GiB a day, projects to about 32 GiB (70% of `/tmp`, 35% of RAM) once the 10-day cleanup starts, leaving about 48 GiB (52%) of RAM available. That leaves memory far from pressure, so the 10-day retention stays: a shorter one would free RAM nothing needs and delete files still in use, such as scripts that running dev tools loaded from `/tmp`. Codex job worktrees belong in `~/code/.worktrees` (`~/.codex/AGENTS.md`, 2026-10-09; the global `CLAUDE.md` dropped the rule in dotfiles `ace7912`, and Claude sessions now start in `claude -w` worktrees under `<repo>/.claude/worktrees`, on disk), yet on 2026-10-23 workflow subagents of a umath_experiment Claude session again copied the repository twice, `node_modules` included, into `/tmp/rv2` (6.6 GiB): bun cannot hardlink across filesystems, so a umath worktree in `/tmp` holds a 1.1 GiB copy of `node_modules` in RAM, while on disk it hardlinks every file from bun's cache.
- `w` owns the machine. `heila` is a separate user with a loop-mounted home at `/home/heila`, their own herdr server and agents, and podman containers. Processes listed under `usbmux` belong to the Supabase containers, whose UID matches that host user.

## Exposure baseline

- ufw denies incoming by default. Its rules, identical for IPv4 and IPv6 except the 10.42.0.0/24 rule: allow anything on `tailscale0`, allow 22/tcp and 2222/tcp on `tailscale0`, allow 22/tcp from 10.42.0.0/24, deny 5678/udp on `wlo1`.
- Docker publishes Supabase on `0.0.0.0:54321-54324`, which bypasses ufw. The `DOCKER-USER` chains from `/etc/ufw/after.rules` and `/etc/ufw/after6.rules` drop forwarded traffic to Docker networks unless it comes from `tailscale0` or a Docker bridge: two DROP rules per address family. ingress-guard's forward chain also drops that Wi-Fi traffic, so either layer alone keeps published ports off the Wi-Fi network.
- `ingress-guard.service` loads `/etc/nftables.d/ingress-guard.nft`, the `inet ingress_guard` table, which filters at prerouting and forward, before ufw. From `tailscale0` it accepts every port from m4, established and related traffic, ICMP from the iPhone and heila's device, from the iPhone TCP 2222, 3000-3999, 5173 and 8000-8999 and UDP 60000-61000 (mosh), and from heila's device TCP 2222 and UDP 60000-61000; it counts and drops the rest, and drops DNAT-ed traffic arriving on `wlo1` or `enp3s0` (see Accepted decisions, 2026-10-11); the file names each device by its tailnet addresses. Tailscale SSH is off (see the sshd entry below), so a device not named here, such as a newly added one, reaches nothing until its addresses are added. Tailscale itself filters nothing here: i9's packet filter accepts every port from every peer, including heila's device, the only shared one since the user revoked i9's reusable share link on 2026-10-11 (that link had also admitted five devices of another account); plain `tailscale status` hides shared devices (they appear with `ShareeNode` in `tailscale status --json`; `sudo tailscale debug netmap` shows the filter and the SSH policy).
- sshd is socket-activated on 22 and 2222, with password and keyboard-interactive authentication and root login off; `AllowUsers` names `w`, `heila` and `i9-tunnel` (see Accepted decisions). Tailscale SSH is off (`RunSSH` false), and has been since 2026-10-29 at the latest: sshd's journal, which begins 2026-10-28, shows m4 on tailnet port 22 from that day, tailscaled's shows no SSH session, and nothing retained records the change. OpenSSH answers m4 on port 22 and heila's device on port 2222, where all 32 of its connections since 2026-10-28 arrived, logging in as `heila` with the key in `/home/heila/.ssh/authorized_keys` (written 2026-11-19), a path set up at the user's request on 2026-11-14. The tailnet policy still carries both SSH rules, a browser check for m4 and the iPhone and an accept for heila's device as `heila` with port forwarding, so `sudo tailscale set --ssh` would have tailscaled answer port 22 ahead of ingress-guard again and admit heila's device there; only the admin console can remove them.
- `webapps-origin.service` loads `/etc/nftables.d/webapps-origin.nft` (2026-10-07), the `inet webapps_origin` table, which filters local output: on 127.0.0.1 it rejects TCP 2019, 20241 and 39093 for every uid but root, caddy and `w`, and it rejects the Docker networks of the `umath` and `umath_2_fresh` stacks for every uid but root. Docker has since added the networks of `umath_3` and `umath_4`, which the rule does not cover, so system accounts reach those stacks' unpublished ports; `heila` and the Airsheen accounts are held by their own guard tables.
- Expected non-loopback listeners: ports 22 and 2222 (systemd socket activation for sshd), docker-proxy on 54321-54324 and on 543N1-543N4 for each umath_N stack, tailscaled on 41641/udp and its tailnet addresses, cloudflared's outbound QUIC sockets, and the DHCP client on `wlo1`.
- caddy serves 127.0.0.1:80 behind the cloudflared tunnel; cloudflared's metrics are on 127.0.0.1:20241.

## Accepted decisions

- 2026-10-07: chrony's networkd-dispatcher `off.d` hook is diverted to `/usr/lib/networkd-dispatcher/off.d-chrony-onoffline.disabled`. On this host it fired only when Docker deleted an interface, where it does nothing, and each such event logged a `networkctl` error and a dispatcher `Failed to get interface` error. The routable hook remains. Verified: three Docker network create-and-remove cycles logged 12 `networkctl` errors before and 0 after, and the next 25 interface events logged no `Failed to get interface` line (210 earlier that boot). Still expected, and unaffected by the divert: `WARNING:Unknown index N seen, reloading interface list` for each new Docker interface, and `ERROR:Unknown interface index N seen even after reload` (at info priority) when an interface disappears before the dispatcher reloads, an upstream race: 286 of the 1,774 Docker interface events from 2026-10-05 to 2026-10-21, up to 66 a day. Undo: `sudo dpkg-divert --local --rename --remove /usr/lib/networkd-dispatcher/off.d/chrony-onoffline`.
- 2026-10-09: `/etc/systemd/network/10-netplan-enp3s0.network.d/optional.conf` sets `RequiredForOnline=no` for `enp3s0`. netplan 1.2 turns `optional: true` only into its drop-in for the boot-time `systemd-networkd-wait-online.service` (`-i wlo1`), but `apt-daily` and `apt-daily-upgrade` run `apt-helper wait-online`, which calls `systemd-networkd-wait-online` without `-i`, so each run waited the full 30 seconds for `enp3s0`, which has no carrier, and logged an error: 18 runs that boot. The drop-in was written on 2026-10-05, but networkd loaded it only at `sudo networkctl reload` on 2026-10-09, which reconfigured `enp3s0` alone. Verified: `systemd-networkd-wait-online --timeout=5` exited 1 after 5.2 seconds before; after, it and `apt-helper wait-online` exit 0 at once. The directory name follows netplan's generated `10-netplan-enp3s0.network`. Undo: `sudo rm -r /etc/systemd/network/10-netplan-enp3s0.network.d && sudo networkctl reload`.
- 2026-10-10: m4's `i9-tunnel` and `agent-sounds-tunnel` LaunchAgents log in to sshd on port 2222 as `i9-tunnel` (uid 101), a system account with no shell or home, instead of through Tailscale SSH.
