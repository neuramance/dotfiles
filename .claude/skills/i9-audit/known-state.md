## Host

- The primary link is Wi-Fi `wlo1`. `enp3s0` is a direct Ethernet link (10.42.0.2/24, `/etc/netplan/70-direct-link.yaml`), usually without carrier. networkd's `off` state means administratively down or being deleted; a Wi-Fi drop is `no-carrier` or `dormant`.
- `/etc/netplan/60-wifi.yaml` and its `.backup-*` copy hold the Wi-Fi password.
- `/tmp` is tmpfs, so its files use RAM, up to half of it. `systemd-tmpfiles-clean` deletes entries older than 10 days and a reboot empties it. Agent work accumulates there, in bursts: on 2026-10-09 at 20:10, 4.6 days after boot, 10.6 GiB had built up; by 23:10 it was 15 GiB (31% of `/tmp`), because a review subagent of a session started before the worktree rule below copied `nm/site` five times, `node_modules` included and not hardlinked, into `/tmp/review-final` (4.2 GiB in 15 minutes). Vitest 5.0.1's leaked temp directories (fixed in 5.0.3; see Accepted decisions, 2026-10-21) held 4.9 GiB and agents' named scratch directories most of the rest. The mean rate, 3.2 GiB a day, projects to about 32 GiB (70% of `/tmp`, 35% of RAM) once the 10-day cleanup starts, leaving about 48 GiB (52%) of RAM available. That leaves memory far from pressure, so the 10-day retention stays: a shorter one would free RAM nothing needs and delete files still in use, such as scripts that running dev tools loaded from `/tmp`. Codex job worktrees belong in `~/code/.worktrees` (`~/.codex/AGENTS.md`, 2026-10-09; the global `CLAUDE.md` dropped the rule in dotfiles `ace7912`, and Claude sessions now start in `claude -w` worktrees under `<repo>/.claude/worktrees`, on disk), yet on 2026-10-23 workflow subagents of a umath_experiment Claude session again copied the repository twice, `node_modules` included, into `/tmp/rv2` (6.6 GiB): bun cannot hardlink across filesystems, so a umath worktree in `/tmp` holds a 1.1 GiB copy of `node_modules` in RAM, while on disk it hardlinks every file from bun's cache.
- `w` owns the machine. `heila` is a separate user with a loop-mounted home at `/home/heila`, their own herdr server and agents, and podman containers. Processes listed under `usbmux` belong to the Supabase containers, whose UID matches that host user.

- NVMe `unsafe_shutdowns` was 39 on 2026-10-07, and still 39 on 2026-10-28.
- The CPU is an i9-13900K (Raptor Lake, subject to Intel's Vmin-shift degradation) on a B760I AORUS PRO, BIOS F14 (2025-09-19, microcode 0x12f, which the OS updates early to 0x133), with PL1 = PL2 = 253 W; its 2×48 GB DDR5-5600 has no ECC. ## Exposure baseline

- ufw denies incoming by default. Its rules, identical for IPv4 and IPv6 except the 10.42.0.0/24 rule: allow anything on `tailscale0`, allow 22/tcp and 2222/tcp on `tailscale0`, allow 22/tcp from 10.42.0.0/24, deny 5678/udp on `wlo1`.
- Docker publishes Supabase on `0.0.0.0:54321-54324`, which bypasses ufw. The `DOCKER-USER` chains from `/etc/ufw/after.rules` and `/etc/ufw/after6.rules` drop forwarded traffic to Docker networks unless it comes from `tailscale0` or a Docker bridge: two DROP rules per address family. ingress-guard's forward chain also drops that Wi-Fi traffic, so either layer alone keeps published ports off the Wi-Fi network.
- `ingress-guard.service` loads `/etc/nftables.d/ingress-guard.nft`, the `inet ingress_guard` table, which filters at prerouting and forward, before ufw. It first counts and drops, on every interface, IPv4 TCP packets carrying IP options (see Accepted decisions, 2026-11-02). From `tailscale0` it accepts every port from m4, established and related traffic, ICMP from the iPhone and heila's device, and from the iPhone alone TCP 2222, 3000-3999, 5173 and 8000-8999 and UDP 60000-61000 (mosh); it counts and drops the rest, and drops DNAT-ed traffic arriving on `wlo1` or `enp3s0` (see Accepted decisions, 2026-10-11); the file names each device by its tailnet addresses. Tailscale SSH on 22 is answered by tailscaled before the kernel firewall sees it, so ingress-guard never gates it; the SSH policy does. A device not named here, such as a newly added one, reaches only Tailscale SSH until its addresses are added. Tailscale itself filters nothing here: i9's packet filter accepts every port from every peer, including heila's device, the only shared one since the user revoked i9's reusable share link on 2026-10-11 (that link had also admitted five devices of another account); plain `tailscale status` hides shared devices (they appear with `ShareeNode` in `tailscale status --json`; `sudo tailscale debug netmap` shows the filter and the SSH policy).
- sshd is socket-activated on 22 and 2222, with password and keyboard-interactive authentication and root login off; `AllowUsers` names `w`, `heila` and `i9-tunnel` (see Accepted decisions). Tailscale SSH is on (`RunSSH`): its policy accepts heila's device as `heila`, and asks m4 and the iPhone for a browser check every 12 hours, which the netmap shows as an accept rule for m4 with `ruleExpires`.
- Expected non-loopback listeners: ports 22 and 2222 (systemd socket activation for sshd), docker-proxy on 54321-54324 and on 543N1-543N4 for each umath_N stack, tailscaled on 41641/udp and its tailnet addresses, cloudflared's outbound QUIC sockets, and the DHCP client on `wlo1`.
- caddy serves 127.0.0.1:80 behind the cloudflared tunnel; cloudflared's metrics are on 127.0.0.1:20241.

- 2026-11-02: ingress-guard's prerouting chain begins with `ip hdrlength > 5 meta l4proto tcp counter drop`, a stopgap for CVE-2026-98432 (CVSS 9.8, fixed upstream in 7.2.10 and 7.3): a use-after-free in `ip_options_build()` when a retransmitted SYN races `tcp_v4_syn_recv_sock()`, which hands the request's IPv4 options to the child socket uncopied. It needs a SYN carrying IPv4 options, and its second trigger, request migration, is off (`net.ipv4.tcp_migrate_req = 0`); IPv6 is unaffected. 7.0.0-38 and 7.0.0-42 are both vulnerable; 7.0.0-43.43, in `resolute-proposed` since 2026-10-28, carries the fix (`ipv4: free inet_opt and ireq_opt after an RCU grace period` in its changelog). It stays uninstalled until it reaches `resolute-updates` or `resolute-security`: a `-proposed` kernel is still in SRU verification, and it takes effect only at the reboot the user defers. The rule stops Wi-Fi, tailnet, loopback and container-to-host packets, including those from local users, who can set `IP_OPTIONS` unprivileged; `umath-browser` uses host networking, so the rule covers it too. It cannot stop a Supabase container's own traffic inside its network namespace, where Docker's default capabilities include `CAP_NET_RAW`; that path presupposes code execution in a pinned Supabase image, and Docker has no daemon-wide capability drop, so closing it would take a per-container hook that the residual risk does not justify. It matches TCP only, because IGMP carries the Router Alert option. Verified at 2026-11-02 under a 240-second automatic revert: `nft -c` accepted the file, m4's established connections to 22 and 2222 survived the reload, m4 opened a new connection to 2222, and loopback services answered. The counter (`sudo nft list chain inet ingress_guard prerouting`) shows matches; it read 0 at install. Remove the rule once `uname -r` reports a kernel whose changelog carries the fix. Undo: `sudo cp -p /var/backups/ingress-guard.nft.20261102 /etc/nftables.d/ingress-guard.nft && sudo systemctl reload ingress-guard`.
