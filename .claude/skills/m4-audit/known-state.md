## Host

- m4 is a MacBook Pro (Mac16,5): Apple M4 Max with 12 performance and 4 efficiency cores, 128 GiB of memory, a 1 TB SSD (APPLE SSD AP1024Z, a 994.7 GB APFS container), and a 140 W adapter. It ran macOS 26.6.2 (25G83) on 2026-10-07.
- `w` is the only user and has no passwordless sudo. macOS has no `timeout`; the snapshot bounds calls with `/usr/bin/perl`. `smartmontools` is not installed.
- `SFA-*.json` diagnostic reports (`bug_type 226`) are periodic keychain-sync analytics, written several times a week, not faults.
- `top`'s POWER column equals its %CPU column here. Battery telemetry (`ioreg -rw0 -c AppleSmartBattery`, `SystemLoad` in milliwatts) refreshes about once a minute.
- Baselines on 2026-10-07, 45 days after boot and awake 54% of that time: 318 GB written to the internal disk per day; Data volume 308 GiB used, container 637 GB free of 995 GB; 1.8 GB of 3 GB swap used at pressure level 1; battery at 314 cycles, Maximum Capacity 92%, Condition Normal; 4% charge lost over 12.8 h from sleep to wake on battery (0.31% per hour); 7-12 W system power with the display on and no heavy job.

## Exposure baseline

A non-loopback listener from a signed program is therefore reachable from the local network. SIP and Gatekeeper are on.
- Expected non-loopback listeners: launchd on 22 for sshd (Remote Login), ControlCenter (AirPlay Receiver) on 5000 and 7000, rapportd (Continuity) and Tailscale (`io.tailscale.ipn`) on ephemeral TCP ports, Tailscale on 41641/udp, netbiosd on 137-138/udp, mDNSResponder and Chrome on 5353/udp, and sharingd, syslogd, and replicatord on ephemeral UDP ports.

## Expected processes and services

- Agent sessions run in herdr panes and iTerm2 tabs. `herdr server`, `codex app-server daemon`, `op daemon` (1Password CLI), and `keyboxd` (GnuPG) run detached by design.
- Each working Claude Code session renews a `caffeinate -i -t 300` child, and Codex sets `prevent_idle_sleep = true`, so their idle-sleep assertions are expected while agents work.
- Dev servers started by agent sessions (`bun run dev`, which runs `next-server`) outlive the session and listen on all interfaces. Judge each by the evidence rules, never by detachment alone. On ports 3000-3099 the `i9-tunnel` holds 127.0.0.1 and ::1, so `localhost` reaches i9, and a local server there is reachable only from other hosts.
- Docker Desktop 4.71.0 keeps `com.docker.backend` and its UI running. Its Linux VM uses Apple's Virtualization framework with 16 CPUs, `MemoryMiB` 16384, and Rosetta for amd64 images; its log (`com.docker.virtualization.log` under `~/Library/Containers/com.docker.docker/Data/log/host`) records VM starts from 2026-04-27 to 2026-10-06. Resource Saver stops the VM after 5 minutes idle, and `docker desktop status` then reports `stopped`. Its `idlemetrics` log line recorded 174 h 39 m of VM compute over 654 h 10 m of running time at its 2026-10-06 stop, about 27% of one core while running. `Docker.raw` is sparse: 24 GiB allocated of 926 GiB.
- LaunchAgents tracked in the dotfiles and described in `~/README.md`: `i9-tunnel` and `agent-sounds-tunnel` (KeepAlive `ssh`, which exits 255 when the network drops; their logs in `~/Library/Logs` hold only the latest attempt). `agent-sounds-tunnel` also exits whenever i9 still holds 127.0.0.1:47123 for a dropped connection and retries every 10 seconds, so its runs count grows by design. `agent-sounds` is socket-activated in inetd style, so launchd's runs count stays 0 and its state `not running` is normal. `local-state` runs daily at 13:00 and backs up `~/.ssh`, AWS configuration, and shell secrets of m4 and i9 to 1Password; it is not a backup of files. `nessie-skill` runs at login, whenever an update replaces `/Applications/Nessie.app`, and whenever `~/.claude/skills` or `~/.codex/skills` changes: it copies the app's bundled `SKILL.md` and `SKILL.codex.md` into `~/.claude/skills/nessie` and `~/.codex/skills/nessie`, and deletes the `submit-skill-feedback` skill the app reinstalls at each launch, so its runs count grows with app launches; between runs its state `not running` is normal, and its log holds only refreshes, removals, and failures. `i9-claude-sync` runs daily at 12:00 and copies i9's Claude Code transcripts into `~/.claude/projects` (directories named `-home-w-*` and `-tmp-*`), so those are i9's sessions, not this Mac's; it notifies only on failure.
- The Claude desktop app runs its own Linux VM (`com.apple.Virtualization.VirtualMachine` holding `~/Library/Application Support/Claude/vm_bundles/claudevm.bundle`); on 2026-10-21 it used 0.8 CPU-minutes in 2 h 45 m, so it is not a load source. The app's Claude Code sessions run as `disclaimer` > `claude --output-format stream-json` children of the app, and the commands they run descend from those.
- Google's updater LaunchAgent runs on an interval, so its runs count grows by design.

## Accepted decisions

- 2026-10-27: herdr comes from its own installer in `~/.local/bin`, as on i9, and is updated with `herdr update`. Homebrew's copy was removed: `~/.local/bin` precedes Homebrew on `PATH`, so it never ran while `brew upgrade` kept updating it. Verified with `which -a herdr` (one path) and `herdr status` (client and server 0.9.3, compatible). Rollback: `brew install herdr` and restore `herdr` in `brew_pkgs` in `~/.config/scripts/mac-setup.sh`.
- 2026-10-27: `python@3.14` stays installed on request and listed in `~/.Brewfile`, because `~/.config/gcloud/virtenv` and `~/code/python-template/.venv` are built on it. Homebrew's autoremove deleted it once as an unneeded dependency, which broke both venvs until it was reinstalled. Rollback: remove the line from `~/.Brewfile`.
- The mise shims ahead of Homebrew on `PATH` are not duplicate installs: `~/.config/mise/config.m4.toml` sets `node = "homebrew"`, so `node`, `npm`, `npx`, and `corepack` resolve to Homebrew's node, and mise serves the `.node-version` and `.nvmrc` pins in `~/code` (24 for most projects, 22 for `sb/SBHub`) from `node@24` and its own 22.23.2. Observed 2026-10-27.
- 2026-10-27: each tool has one install. `gemini` and `ntn` are the npm globals `~/.Brewfile` declares; the bun global `@google/gemini-cli` 0.1.1 that shadowed `gemini` 0.53.1 and the standalone `~/.local/bin/ntn` were removed (the npm `ntn` reads the same keychain login, verified with `ntn doctor`; `ntn update` replaces the running binary in place). uv's unused cpython 3.13.5 and 3.11.13 were uninstalled, so `python3.13` is Homebrew's. Rollback: `bun add -g @google/gemini-cli`, `curl -fsSL https://ntn.dev | bash`, `uv python install 3.13 3.11`.
- 2026-10-27: zsh PATH lines that look duplicated are deliberate. macOS's `path_helper` in `/etc/zprofile` moves the `~/.local/bin` and mise entries from `.zshenv` behind Homebrew and `/usr/bin` in login shells, so `.zprofile` prepends them again; `.zshrc` prepends `~/.local/bin` once more to keep it ahead of `~/.bun/bin`. `/usr/lib/postgresql/18/bin` in `.zshenv` exists only on i9. The grok installer's block in `.zshrc` runs a second `compinit -C` (about 6 ms of a 70 ms startup) that loads grok's completions from `~/.zcompdump`; it is left to the installer. The Solana, `python3 -m site --user-base`, and uv `env` lines were removed: their directories exist on neither host or were already on `PATH`.
